# 第 15 章：计算与控制上下文预算

到第 14 章，Agent 能保存讨论、创建分支，也能核对和恢复受支持工具的文件修改。任务越做越长，另一个限制开始出现：每次请求模型时，程序会把系统提示词、工具说明和历史消息一起发过去。一次很长的测试结果，不只占一次屏幕，还可能跟着后面的每次请求重复发送。

本章仍围绕加法小项目展开。Agent 运行测试，工具返回日志，模型根据日志决定是否需要继续检查。我们要让这条链路在有限的上下文窗口里继续工作：先知道请求大约有多大，再限制单份工具结果进入历史的长度，最后在每次请求前决定预算是否允许继续。

## 预算管理的是一次请求能装下什么

**上下文窗口**是模型一次处理输入与生成输出所能容纳的 Token 数量范围。Token 是分词器处理文本后的单位，既不固定等于一个汉字，也不固定等于一个英文单词。对我们正在构建的 Agent 来说，关键是把即将发送的内容与为回答保留的空间放在一起看。

假设一次请求的输入估算是 6,000 Token，为本次输出预留 2,000，配置的窗口是 8,000，那么预算已经用满。即使聊天窗口只显示最后一行问题，历史工具结果和工具说明仍在请求里，不能只数草稿中的文字。

| 数字或内容 | 什么时候知道 | 用来做什么 |
| --- | --- | --- |
| 输入估算 | 发送之前 | 预测本次请求是否还有空间 |
| 输出预留 | 发送之前 | 给模型接下来的生成留出空间，并约束请求参数 |
| 服务返回的实际用量 | 响应之后，且服务提供时 | 说明这次请求实际报告了多少输入与输出 Token |
| 工具完整结果 | 工具执行结束后 | 供本地核对；进入模型历史的版本可以更短 |

估算服务于请求前的判断，实际用量服务于请求后的观察。两者不能相互冒充。只有服务返回输入、输出用量，而且用户配置了两种单价时，程序才另算费用估计；缺少任何一项就不显示。这个估计没有计入缓存、折扣等账单规则，不能当作实际扣费。
