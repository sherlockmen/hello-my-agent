# 第 34 章：让故障可定位、可恢复

测试已经通过，Agent 却在真实任务中停住了。屏幕上最后一行是“正在请求模型”：我们还不知道是限流、断线，还是工具一直没有返回。直接再跑一次也不稳妥——上一次可能已经改了文件，只是最终回答没到。

本章沿用第 33 章的执行边界，为一次运行留下足够的证据，再决定哪些步骤能重试、哪些步骤必须停下核对。我们不把“重新开始整轮任务”当作通用恢复方法。

| 小节 | 我们要回答的问题 | 运行后的变化 |
| --- | --- | --- |
| [34.1 关联一次运行的日志](/content/chapter-34-reliability/01-correlated-logs/README.md) | 哪次模型请求或工具操作卡住了？ | 一个 runId 串起阶段、耗时、用量和结果，诊断文件不含任务正文。 |
| [34.2 只重试可以安全重发的请求](/content/chapter-34-reliability/02-safe-retries/README.md) | 限流或断线后，究竟重发哪一步？ | 只重发尚未显示文字的模型请求；有限退避，取消立即结束等待。 |
| [34.3 停止无进展任务并保留成果](/content/chapter-34-reliability/03-stop-and-diagnose/README.md) | 停止请求发出后，什么时候才算停好？ | 无进展时请求取消，等待原任务收尾，再报告状态、保留物和诊断位置。 |

三个小节都是完整累计快照。34.1 从 33.3 继续，34.2 从 34.1 继续，34.3 从 34.2 继续；本章不移除 LSP、sandbox、扩展、子任务、工作区或会话恢复能力。

诊断日志、会话历史和工具完整输出承担不同职责：日志解释执行过程，历史保存已提交对话，完整输出保存被裁剪的工具正文。日志不代替会话备份，取消不撤销已完成的文件修改，也不保证远端请求没有计费。
