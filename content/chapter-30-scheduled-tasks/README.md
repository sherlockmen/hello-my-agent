# 第 30 章：定时任务——保存规则，让运行中的程序按时调查

[上一章：共享任务](/content/chapter-29-shared-tasks/README.md) · [课程目录](/content/README.md) · [下一章：扩展包](/content/chapter-31-extension-packages/README.md)

第 29 章让多个只读 worker 围绕同一份任务清单工作，模型收到任务状态和消息后，能决定接下来调查什么。本章换一个触发来源：用户预先保存“每隔一分钟检查 README 中的待办”，程序在到期时启动调查，不需要每次重新输入问题。

这里的定时任务由两部分组成。磁盘定义保存做什么、多久检查一次和最多允许花多少预算；运行中的调度器观察时间，决定现在是否启动。保存成功以后，即使退出终端，定义还在；但没有 `serve` 进程时没有人检查时间，也就不会触发。它还不是操作系统服务、云端任务或电脑休眠时仍能工作的闹钟。

## 本章怎样接入已有 Agent

每次到期仍交给已有 `runSubagent`：程序创建新的只读子历史，模型提出读取请求，工具把真实观察交回子模型，子模型再回答或继续调查。最后，调度器把子结果、请求次数和本地 token 预留写入运行记录。用户在 `list` 中看见的是这份已提交记录；不会把一次定时启动混入正在聊天的父历史。

时间到不等于可以无限执行。程序必须同时确认定义为 enabled、同一编号没有正在运行的实例、尝试次数和累计预算还有余额。它先保存 running 记录并扣掉本次预留，保存成功以后才调用模型。因此，文件不是一张无约束的提示词列表，而是一份由本地程序解释的有限计划。

## 一次规则与多次尝试分开保存

例如 `docs` 定义规定一分钟一个间隔、最多三次尝试。每次真正启动都有独立运行编号，而定义只累加次数与 token 预留。失败、取消和崩溃都不能把计数归零，否则重新启动程序就能越过总预算。

本章选择“错过多个间隔，只合并执行一次”。关闭两小时后重新启动，不会立刻补跑 120 次。若上次进程留下 running，程序也不会猜测已经完成还是尚未执行；30.3 要求显式恢复，保留 interrupted 记录并暂停该定义，之后由用户核对再决定是否 resume。

## 实现范围

存储目录默认是 `~/.hello-my-agent/schedules`，示例使用项目内 `.agent-schedules` 便于查看。一个动作或整个 serve 生命周期独占存储；serve 运行期间，另一个 CLI 即使只执行 list 也会收到占用提示。控制当前服务，要在它的标准输入里输入 list、pause、resume 或 stop；Ctrl+C 关闭服务并等待真实任务收尾。

任务只保存提示、创建时的真实工作区、时间和预算，不保存密钥、工具授权或任意工具配置。serve 从当前环境重新读取连接配置，每次子任务都从空授权开始。提示与摘要仍是明文，不应主动把凭据放进去。创建和运行要在同一真实工作区进行，程序不会靠切换全局目录来并行处理不同项目。
