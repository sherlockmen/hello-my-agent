# 第 28 章：让修改拥有独立工作区与可核对的版本

两个任务同时编辑同一个项目目录，即使各自的模型历史独立，也可能覆盖同一文件。本章用Git worktree给任务各自的工作文件、索引与分支，再把评审、整合和清理分别绑定到可检查的版本事实。

新工作区从原目标分支当前HEAD提交开始。原目录尚未提交的修改、未跟踪文件与被忽略文件仍留在原处，不会自动复制过去。创建结果给出仓库、目标分支、base SHA、任务分支、路径和会话ID；模型用这个ID逐次请求在对应目录执行命令，读、改、测与提交仍要经过原权限链和审批。

## 从一份任务成果到原目标分支

任务提交提供稳定的候选版本。评审时同时固定目标SHA和任务SHA，先确认两边干净且没有未结束Git操作，再展示完整差异。用户批准的是这两个版本之间的变化；任意一端移动或出现未提交修改，原批准就失效。

整合执行前再核对批准依据，使用被审任务提交进行真实合并。成功需要进程正常结束、目标保持正确分支且干净、没有未结束操作，并能证明候选提交已经进入目标历史。测试仍需依据任务要求实际执行；合并成功本身不证明功能正确。

清理还要确认任务当前提交已被目标包含，目录里没有未保存或被忽略文件。获得单独批准并完成删除后，再核对目录与Git登记都已消失。冲突、取消或检查失败时保留真实现场和任务分支，模型根据工具观察解释下一步；CLI退出也不会自动删除任务成果。

第25章隔离子Agent的推理历史，第27章限制工具调用的同时执行范围，本章隔离任务修改的目录。只读子Agent并未因此获得写权限，工作区工具仍是串行屏障。独立目录也不是命令沙箱：获批命令和可信仓库的本地Git配置仍可能执行程序或访问其他路径。

运行各节完整快照使用 `npm run lesson:28.1`、`npm run lesson:28.2`、`npm run lesson:28.3`；配套仓库的 `npm run check:28` 在本地临时Git仓库检查身份、版本、审批、冲突和清理，不调用在线模型。
