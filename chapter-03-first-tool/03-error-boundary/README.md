# 03.3 把工具失败反馈给模型

[上一节：执行 read_file](../02-read-file-loop/README.md) · [第三章首页](../README.md) · [本节源码](src/) · [练习与答案](../EXERCISES.md)

**本节目标：把可预期工具错误作为结果发回模型，并确保取消、意外异常和超限不会污染会话历史。**

## 问题

03.2 已经能在 `read_file` 成功时把文件内容发回模型，并继续循环到最终回答。但工具请求不一定成功：

```text
read_file({})
read_file({ path: "missing.ts" })
run_magic({})
```

第一种缺少参数，第二种文件不存在，第三种请求了程序没有提供的工具。这些失败需要分成四个问题处理：

1. **模型怎样知道工具失败了？** 如果程序一遇到错误就结束，模型看不到失败原因，无法改正路径、换用其他办法，或向用户解释为什么无法继续。
2. **哪些错误可以留在循环中？** 文件不存在、参数错误和工具未注册属于本次工具调用的结果，可以反馈给模型；取消请求和程序内部异常不能伪装成普通工具结果继续运行。
3. **怎样限制失败重试次数？** 模型可能反复提出同一个无效请求。程序必须继续遵守 8 次上限，避免循环一直消耗时间和 token。
4. **失败时怎样保持正式历史不变？** 工具错误可以暂时加入本轮上下文，帮助模型修正；只有整轮得到最终回答后，这些消息才能一起进入正式历史。

因此，本节要解决的问题是：**怎样把可恢复的工具失败作为结果反馈给模型，同时让取消、程序错误和循环超限安全停止，并保持历史不变？** 本节只处理工具失败时哪些情况继续、哪些情况停止，不增加新的工具。

## 解决方案

只捕获工具层主动创建的 `ToolError`，把它转换成 `isError: true` 的工具结果。其他异常继续向外传播。Agent Loop 沿用 03.2 的 8 次上限，整轮消息仍在最终成功后一次提交。

```text
+-------------+      +-------+      +----------------+
| user prompt | ---> | Model | ---> | final answer？ |
+-------------+      +---^---+      +-------+--------+
                         |                  | 是 --> 提交 turn --> 返回
                         |                  | 否
                         |                  v
                         |          +----------------+
                         |          | executeTool    |
                         |          +-------+--------+
                         |                  v
                         |               成功？
                         |          +-------+-------+
                         |          | 是            | 否
                         |          v               v
                         |   isError=false    是 ToolError？
                         |                    | 是 -> isError=true
                         |                    | 否 -> 抛出，turn 不提交
                         |          +---------+---------+
                         |                    |
                         +--------------------+
                              同一调用 ID 返回模型

每次调用模型前、执行工具前和提交前检查取消
第 8 次仍请求工具 -> 不执行该工具，停止且不提交 turn
```

## 工作原理

### 第一步：区分预期失败和程序故障

`ToolError` 只表示工具执行入口已经预见并安全描述的失败，例如：

- 参数不是 JSON。
- `path` 缺失、为空或多出字段。
- 目标不存在、不是普通文件或超过大小上限。
- 真实路径离开项目根目录。
- 请求读取 `.env` 系列凭据文件。
- 工具名称没有注册。

这些文案不包含堆栈、绝对路径、请求头或密钥，可以作为工具结果交给模型。

其他异常可能来自程序缺陷、内存不足或 SDK 内部错误。代码不能把任意 `error.message` 塞进模型上下文，因为其中可能包含敏感环境信息。因此捕获分支必须判断具体错误类型：

```ts
try {
  const content = await executeTool(call);
  turn.push({
    role: "tool",
    toolCallId: call.id,
    content,
    isError: false,
  });
} catch (error) {
  if (!(error instanceof ToolError)) throw error;
  turn.push({
    role: "tool",
    toolCallId: call.id,
    content: `工具执行失败：${error.message}`,
    isError: true,
  });
}
```

最容易误解的是“捕获错误等于忽略错误”。这里没有忽略：错误被转换成协议中的显式结果，并保留原调用 ID。模型会看到执行失败，而不是得到一个假的空文件。

### 第二步：工具错误为什么仍要继续循环

Agent 的下一步应基于环境反馈动态决定。以文件不存在为例：

```text
模型请求 read_file({ path: "src/client.ts" })
  -> 本地结果：文件不存在
  -> 模型根据错误决定：
       1. 请求另一个已知路径
       2. 向用户询问文件位置
       3. 返回最终回答，说明当前无法读取
```

程序无法预先知道哪一种最合适，所以它把真实反馈加入上下文，再让模型决定。固定脚本通常会把失败分支预先写死；Agent Loop 的特点是模型根据每次反馈选择下一步，但可执行边界和停止条件仍由程序控制。

错误结果在两种协议中的形式不同：

```text
OpenAI:    role=tool, tool_call_id=call_42, content="工具执行失败..."
Anthropic: type=tool_result, tool_use_id=call_42, is_error=true
```

本地 `Message` 使用统一的 `isError`。OpenAI 没有对应布尔字段，错误事实通过文本表达；Anthropic 适配层还会把它映射到 `is_error`。

### 第三步：未知工具为什么也走结果分支

模型只能看到已声明的 `read_file`，但仍可能生成错误名称；旧历史或不完全兼容的服务也可能返回未知工具。注册表不会动态查找同名函数，而是抛出：

```text
ToolError: 未知工具：run_magic
```

Agent Loop 把它配回原请求。模型可以改用 `read_file`，也可以说明当前没有所需能力。无论模型怎样措辞，本地都没有执行未登记操作。

### 第四步：沿用 8 次模型请求上限

循环变量 `modelCall` 从 1 到 8。每完成一次 `model.generate()`，就消耗一次机会：

```ts
for (let modelCall = 1; modelCall <= MAX_MODEL_CALLS; modelCall += 1) {
  const result = await model.generate(...);
  // 最终回答则 return；工具请求则执行并继续
}
```

一个响应中有三个并列工具调用，仍只算一次模型请求；三个工具都会执行并返回后，下一次 `generate()` 才算第二次。这个计数方式与成本和停止判断一致，因为模型请求才会消耗模型 token。

第 8 次仍返回工具请求时，程序在执行工具前停止。原因是已经没有第 9 次模型调用可以接收工具结果；继续读取只会消耗资源，以后换成有副作用的工具还可能造成无法继续判断的修改。共享 `history` 没有改变，因为提交语句只存在于最终回答分支。

### 第五步：本轮状态的生命周期

一轮执行包含两种状态：

```text
history：以前已经完成的回合，调用方持有
turn：本轮候选消息，agentLoop 内部持有
```

各分支的状态变化如下：

| 分支 | `turn` | `history` |
| --- | --- | --- |
| 工具成功 | 追加请求和结果 | 不变 |
| 工具错误 | 追加请求和错误结果 | 不变 |
| 得到最终回答 | 追加回答 | 一次性追加整个 `turn` |
| 取消、意外异常、超限 | 函数结束后丢弃 | 不变 |

`turn` 只存在于内存。进程退出后，第三章的整个 `history` 也会消失；会话持久化到第 13 章再实现。

### 第六步：取消为什么不作为工具错误

取消表示使用者不再希望当前工作继续，它不是 `read_file` 的业务结果。`AbortSignal.throwIfAborted()` 位于每次模型调用前、工具执行前和提交历史前。一旦取消，函数立即抛出 `AbortError`，不会再请求模型，也不会把“用户取消”伪装成可继续推理的文件结果。

本章的文件读取很快，Node.js `readFile()` 暂未接收取消信号。第 07、08 章处理长时间子进程和流式请求时，会把取消传播到正在运行的操作。

## 动手构建

### 本节修改哪些文件

| 文件 | 状态 | 职责 |
| --- | --- | --- |
| `src/agent/agent-loop.ts` | 修改 | 捕获安全工具错误并生成错误结果；沿用有界循环与原子提交 |

工具参数校验、注册表和协议转换沿用 03.2。本节只改变失败在 Agent Loop 中的含义。

### 1. 只捕获 `ToolError`

从共用错误模块导入错误类型：

```ts
import { ToolError } from "../errors.js";
```

在每次 `executeTool()` 外加入前面展示的 `try/catch`。不要写成 `catch (error) { return String(error) }`；那会同时吞掉程序故障并泄露未知错误内容。

### 2. 保留调用 ID 和错误标记

错误结果使用原 `call.id`：

```ts
turn.push({
  role: "tool",
  toolCallId: call.id,
  content: `工具执行失败：${error.message}`,
  isError: true,
});
```

下一轮模型请求会同时看到原工具请求和这条结果。缺少任意一条，消息链都不完整。

### 3. 保留最终提交点

`history.push(...turn)` 仍只位于最终回答分支。不要在每次工具执行后直接写共享历史，否则第 8 次超限或请求取消时会留下半轮状态。

### 4. 构建并运行

在仓库根目录执行：

```bash
npm run lesson:03.3
```

```bash
hello-my-agent --prompt "请读取 definitely-missing.txt；如果不存在，请说明真实错误。"
```

模型应根据工具错误说明文件不存在。它也可能再请求其他路径，但总模型请求次数不会超过 8。

## 本节实现清单

- 参数错误、文件不存在和未知工具会生成错误工具结果。
- 错误结果保留原调用 ID，并标记 `isError: true`。
- 只有 `ToolError` 的安全文案会进入模型上下文。
- 模型可以根据失败修正请求或返回说明。
- 沿用一轮最多调用模型 8 次的边界；最后一次仍请求工具时不再执行。
- 取消、意外异常和超限不会提交半段历史。
- 最终回答返回本轮所有模型请求的累计用量。

## 运行验证

执行：

```bash
npm run check:03
```

验收会固定触发凭据文件拒绝、成功读取、参数错误、文件不存在和未知工具。随后让模拟模型连续请求 8 次，并用工具参数 getter 统计实际执行次数：前 7 次会读取参数，第 8 次在执行前停止，第 9 次模型调用不会发生，共享历史仍为空。另一个场景会在工具完成后取消，确认第二次模型请求不会发生。最后通过本地 HTTP 接口验证 OpenAI 和 Anthropic 的调用 ID 都正确配对。

## 失败实验：让模型永远请求工具

真实模型不容易稳定复现无限调用，因此使用本地验收中的内存模型：它每次都返回一个新的 `read_file` 请求，从不返回最终文本。

运行 `npm run check:03` 后，检查会确认：

```text
 模型调用次数 = 8
 第 9 次调用 = 没有发生
 第 8 次请求的工具 = 没有执行
 history = []
 错误提示包含“8 次”
```

工具执行次数由参数 getter 直接记录，因此这些检查能证明循环既有上限，也不会执行无法反馈的最后一批工具，更没有把失败轮次提交到会话。

## 小练习

如果同一次模型响应包含两个 `read_file` 请求，程序应该先再次调用模型，还是先执行两个工具？

答案：先按顺序执行两个工具，把两个带各自调用 ID 的结果都加入 `turn`，然后再调用模型。否则第二个工具请求会缺少结果，协议消息链不完整。请在 [本章练习](../EXERCISES.md) 中运行完整的内存模型答案。

## 本节完成后的 Agent

第三章结束时，Agent 已经具备一条有边界的工具循环：

```text
模型决策
   |-- 最终回答 --> 提交完整历史并结束
   |
   +-- 工具请求 --> 注册表分发 read_file
                         |-- 成功结果 --|
                         +-- ToolError -|-> 回传模型并继续决策

取消、系统异常或达到 8 次模型调用上限 --> 放弃未完成回合
```

它可以读取一个已经知道路径的文件，却无法根据“找到登录逻辑”这样的目标发现相关文件和代码位置。第四章将在同一条工具循环中加入文件发现、内容搜索和分段读取，建立完整的只读代码检索链。
