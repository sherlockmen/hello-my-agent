# 03.3 把工具失败反馈给模型

[上一节：执行 read_file](../02-read-file-loop/README.md) · [第三章首页](../README.md) · [本节源码](src/) · [练习与答案](../EXERCISES.md)

**本节目标：把可预期工具错误作为结果发回模型，并确保取消、意外异常和超限不会污染会话历史。**

## 问题：文件不存在，模型却没有收到结果

03.2 已经让模型读到文件后再回答。现在换一个路径：

```text
请读取 definitely-missing.txt；如果不存在，请说明真实错误。
```

模型请求 `read_file`，本地工具找不到文件，抛出错误。上一节会直接结束这一轮，终端能看到错误，模型却只知道自己提出过读取请求，还不知道失败原因。

“文件不存在”其实也是对这次请求的有效回答。模型收到它，才能决定换一个已知路径、询问用户，或者说明当前无法读取。这一节就把这类预期内的失败作为工具结果发回去。

同时，用户取消和程序内部异常仍要停止任务。我们要让模型有机会根据文件读取错误调整下一步，不能让所有异常都变成继续尝试的理由。

## 解决方案：失败也带着原调用 ID 回去

读取工具已经用 `ToolError` 表示参数不对、文件不存在等预期失败，里面放的是程序专门准备的错误说明。Agent Loop 捕获这种错误后，生成一条 `isError: true` 的工具消息，仍使用原来的调用 ID。

模型下一次收到的就是“这次读取失败了，原因是……”。它随后怎样处理，由模型根据任务决定。其他异常继续抛给外层，8 次模型请求上限也保持不变。

```text
+-------------+      +-------+      +----------------+
| user prompt | ---> | Model | ---> | final answer？ |
+-------------+      +---^---+      +-------+--------+
                         |                  | 是 --> 提交 turn --> 返回
                         |                  | 否
                         |                  v
                         |          +----------------+
                         |          | executeTool    |
                         |          +-------+--------+
                         |                  v
                         |               成功？
                         |          +-------+-------+
                         |          | 是            | 否
                         |          v               v
                         |   isError=false    是 ToolError？
                         |                    | 是 -> isError=true
                         |                    | 否 -> 抛出，turn 不提交
                         |          +---------+---------+
                         |                    |
                         +--------------------+
                              同一调用 ID 返回模型

每次调用模型前、执行工具前和提交前检查取消
第 8 次仍请求工具 -> 不执行该工具，停止且不提交 turn
```

## 工作原理

沿着刚才不存在的文件，看错误怎样回到模型：

```text
1. 用户要求读取 definitely-missing.txt，模型返回 read_file 请求
2. 本地工具校验路径时发现文件不存在，抛出 ToolError
3. Agent Loop 只捕获这个可安全描述的工具错误
4. Agent Loop 用原调用 ID 生成 isError=true 的工具结果
5. 错误结果回到模型，模型可以改用其他路径或解释无法读取
6. 模型给出最终回答后，完整本轮才进入 history 并交给终端显示
```

如果发生取消、程序内部异常或第 8 次模型请求后仍没有最终回答，第 4 步不会把它伪装成普通工具结果；Agent Loop 直接停止，本轮消息不进入正式历史。

### 哪些错误可以告诉模型

`ToolError` 是本地工具专门定义的错误类型。创建它时，程序已经知道失败属于哪种情况，也准备好了可以对外说明的文字，例如：

- 参数不是 JSON。
- `path` 缺失、为空或多出字段。
- 目标不存在、不是普通文件或超过大小上限。
- 真实路径离开项目根目录。
- 请求读取 `.env` 系列凭据文件。
- 工具名称没有注册。

这些说明由程序编写，可以带上本次请求中的路径或工具名，但不会直接附上底层异常的堆栈、请求头或响应体。定义这个错误类型的目的，是让主循环能认出“这是一条准备好给模型看的工具失败说明”。

其他异常可能来自程序缺陷、内存不足或 SDK 内部错误。代码不能把任意 `error.message` 塞进模型上下文，因为其中可能包含敏感环境信息。因此捕获分支必须判断具体错误类型：

```ts
try {
  const content = await executeTool(call);
  turn.push({
    role: "tool",
    toolCallId: call.id,
    content,
    isError: false,
  });
} catch (error) {
  if (!(error instanceof ToolError)) throw error;
  turn.push({
    role: "tool",
    toolCallId: call.id,
    content: `工具执行失败：${error.message}`,
    isError: true,
  });
}
```

捕获以后，程序仍然保存了失败事实。`isError: true` 表示执行失败，`content` 说明原因，`toolCallId` 说明哪次请求失败。若只返回空字符串，模型就无法区分“文件是空的”和“文件根本没有读到”。

本节只区分“模型可以修正的工具错误”和“必须中止的程序故障”；第 34 章会继续细分可重试错误、退避条件和无进展失败。

### 模型收到失败后，下一步由谁决定

Agent 的下一步应基于环境反馈动态决定。以文件不存在为例：

```text
模型请求 read_file({ path: "src/client.ts" })
  -> 本地结果：文件不存在
  -> 模型根据错误决定：
       1. 请求另一个已知路径
       2. 向用户询问文件位置
       3. 返回最终回答，说明当前无法读取
```

程序不知道用户希望继续找文件，还是只想确认它不存在，因此不在读取工具里写死下一步。它把失败结果发回模型，模型结合原始要求继续判断。当前还没有搜索工具，模型只能尝试已经知道的路径；第四章会补上主动查找文件的能力。

错误结果在两种协议中的形式不同：

```text
OpenAI:    role=tool, tool_call_id=call_42, content="工具执行失败..."
Anthropic: type=tool_result, tool_use_id=call_42, is_error=true
```

本地 `Message` 使用统一的 `isError`。OpenAI 没有对应布尔字段，错误事实通过文本表达；Anthropic 适配层还会把它映射到 `is_error`。

### 请求了不存在的工具，也要得到明确结果

模型只能看到已声明的 `read_file`，但仍可能生成错误名称；旧历史或不完全兼容的服务也可能返回未知工具。注册表不会动态查找同名函数，而是抛出：

```text
ToolError: 未知工具：run_magic
```

Agent Loop 把它配回原请求。模型可以改用 `read_file`，也可以说明当前没有所需能力。无论模型怎样措辞，本地都没有执行未登记操作。

### 允许调整请求，不等于无限重试

循环变量 `modelCall` 从 1 到 8。每完成一次 `model.generate()`，就消耗一次机会：

```ts
for (let modelCall = 1; modelCall <= MAX_MODEL_CALLS; modelCall += 1) {
  const result = await model.generate(...);
  // 最终回答则 return；工具请求则执行并继续
}
```

一个响应中有三个并列工具调用，仍只算一次模型请求；三个工具都会执行并返回后，下一次 `generate()` 才算第二次。这个计数方式与成本和停止判断一致，因为模型请求才会消耗模型 token。

第 8 次仍返回工具请求时，程序在执行工具前停止。原因是已经没有第 9 次模型调用可以接收工具结果；继续读取只会消耗资源，第 06 章加入写入、第 07 章加入 Shell 后还可能产生无法继续判断的副作用。共享 `history` 没有改变，因为提交语句只存在于最终回答分支。

### 失败结果先放在哪里

一轮执行包含两种状态：

```text
history：以前已经完成的回合，调用方持有
turn：本轮候选消息，agentLoop 内部持有
```

各分支的状态变化如下：

| 分支 | `turn` | `history` |
| --- | --- | --- |
| 工具成功 | 追加请求和结果 | 不变 |
| 工具错误 | 追加请求和错误结果 | 不变 |
| 得到最终回答 | 追加回答 | 一次性追加整个 `turn` |
| 取消、意外异常、超限 | 函数结束后丢弃 | 不变 |

`turn` 只存在于内存。进程退出后，第三章的整个 `history` 也会消失；会话持久化到第 13 章再实现。

### 用户取消以后，就不再请模型继续

取消表示使用者不再希望当前工作继续，它不是 `read_file` 的业务结果。`AbortSignal.throwIfAborted()` 位于每次模型调用前、工具执行前和提交历史前。取消后运行到检查点时，`throwIfAborted()` 会抛出取消异常，停止继续执行。程序不会把“用户取消”伪装成一个让模型继续推理的文件结果。

本章的文件读取很快，Node.js `readFile()` 暂未接收取消信号。第四章会先把取消信号传进文件遍历和读取；第 07、08 章再扩展到子进程和流式请求。同步操作要等到可检查信号的位置才能停下，传入信号不等于任何时刻都能中断。

## 动手构建

本节只修改 `agent/agent-loop.ts`。读取工具已经会抛出 `ToolError`，模型适配层也已经能转换错误结果，我们把这两端接起来即可。

### 1. 导入工具错误类型

把文件顶部从 `errors.ts` 导入的那一行替换为：

```ts
import { ToolError, UserFacingError } from "../errors.js";
```

### 2. 替换执行同批工具的循环

找到 `turn.push()` 保存 assistant 工具请求之后的 `for (const call of result.toolCalls)`。用下面的完整循环替换它，外层模型循环、用量累计和最终回答分支保持不变：

```ts
    for (const call of result.toolCalls) {
      signal.throwIfAborted();
      try {
        const content = await executeTool(call);
        turn.push({ role: "tool", toolCallId: call.id, content, isError: false });
      } catch (error) {
        // [CHANGED 03.3] 预期内的工具错误回到循环；编程错误、系统异常仍交给外层处理。
        if (!(error instanceof ToolError)) throw error;
        turn.push({
          role: "tool",
          toolCallId: call.id,
          content: `工具执行失败：${error.message}`,
          isError: true,
        });
      }
    }
```

成功和 `ToolError` 两条路都添加一条工具结果。其他异常会从 `catch` 再次抛出，不会落到“继续请求模型”的路径。

### 3. 保留整轮完成后才保存历史的规则

`history.push(...turn)` 仍只放在最终回答分支。工具错误现在能暂存在 `turn` 中供模型继续使用，但不等于这一轮已经完成。

## 运行验证

执行：

```bash
npm run check:03
```

验收会固定触发凭据文件拒绝、成功读取、参数错误、文件不存在和未知工具。随后让模拟模型连续请求 8 次，并用工具参数 getter 统计实际执行次数：前 7 次会读取参数，第 8 次在执行前停止，第 9 次模型调用不会发生，共享历史仍为空。另一个场景会在工具完成后取消，确认第二次模型请求不会发生。最后通过本地 HTTP 接口验证 OpenAI 和 Anthropic 的调用 ID 都正确配对。

## 失败实验：让模型永远请求工具

真实模型不容易稳定复现无限调用，因此使用本地验收中的内存模型：它每次都返回一个新的 `read_file` 请求，从不返回最终文本。

运行 `npm run check:03` 后，检查会确认：

```text
 模型调用次数 = 8
 第 9 次调用 = 没有发生
 第 8 次请求的工具 = 没有执行
 history = []
 错误提示包含“8 次”
```

工具执行次数由参数 getter 直接记录，因此这些检查能证明循环既有上限，也不会执行无法反馈的最后一批工具，更没有把失败轮次提交到会话。

## 小练习

如果同一次模型响应包含两个 `read_file` 请求，程序应该先再次调用模型，还是先执行两个工具？

答案：先按顺序执行两个工具，把两个带各自调用 ID 的结果都加入 `turn`，然后再调用模型。否则第二个工具请求会缺少结果，协议消息链不完整。请在 [本章练习](../EXERCISES.md) 中运行完整的内存模型答案。

## 本节完成后的 Agent

第三章结束时，成功和预期失败都能回到模型，循环也有了明确的停止条件：

```text
模型决策
   |-- 最终回答 --> 提交完整历史并结束
   |
   +-- 工具请求 --> 注册表分发 read_file
                         |-- 成功结果 --|
                         +-- ToolError -|-> 回传模型并继续决策

取消、系统异常或达到 8 次模型调用上限 --> 放弃未完成回合
```

它可以读取一个已经知道路径的文件，却无法根据“找到登录逻辑”这样的目标发现相关文件和代码位置。第四章将在同一条工具循环中加入文件发现、内容搜索和分段读取，建立完整的只读代码检索链。
