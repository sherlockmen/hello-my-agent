# 第 03 章：第一个工具与 Agent Loop

[全书目录](../README.md) · [03.1 识别工具请求](01-tool-request/README.md) · [03.2 执行并回传](02-read-file-loop/README.md) · [03.3 工具失败反馈](03-error-boundary/README.md) · [练习与答案](EXERCISES.md)

第二章中，我们已经能在终端连续提问，程序也会把之前的问答带给模型。但模型看到的仍然只有消息里的文字。项目中的文件即使就在电脑上，只要程序没有读取并发送，模型就不知道里面写了什么。

这一章，我们给 Agent 加入第一个工具 `read_file`。模型需要文件时，先提出读取请求；本地程序检查请求、读取文件，再把内容发回模型。这样，模型才有机会根据当前项目里的真实内容回答。

前两章已经完成的命令能力继续保留：`hello-my-agent --doctor` 可以在不读取模型配置的情况下显示运行环境，连续会话中的 `/reset` 可以清空历史且不会发送给模型。本章只在这些能力之上增加工具请求和执行循环。

## 问题：模型说“读取文件”，并不会让操作系统真的打开文件

在项目目录中提出这样一个要求：

```text
请读取 package.json，告诉我这个包叫什么。
```

只有文本对话能力时，模型面临两个选择：承认不知道，或者根据上下文猜测。即使它说“我会读取文件”，这句话也不会触发操作系统打开文件。模型调用和文件系统属于两个不同的执行环境：

- 模型服务接收消息并返回一次结果。
- 本地 Agent 进程拥有文件系统 API，可以真正读取文件。

连接这两个环境，要靠一次来回：模型用约定的格式说出要读哪个文件，程序读完后，把内容作为这次请求的结果发回去。模型收到内容，才继续回答包名。

这次来回也会改变 `agentLoop()`：第二章的一次模型请求，可能变成“请求模型 → 读取文件 → 再请求模型”。我们会逐步接通这个循环，再让文件不存在这样的失败也能回到模型。

## 完整执行模型

### 模型不能直接调用本地函数

平时说“模型调用了工具”，省略了中间的程序。实际运行时，模型返回的仍是数据，只是这次数据写明了工具名和参数。本地程序收到后，才去调用对应函数。

```text
模型返回：
{
  id: "call_42",
  name: "read_file",
  arguments: "{\"path\":\"package.json\"}"
}

本地程序执行：
readFileTool('{"path":"package.json"}')
```

这份请求中的 `read_file` 是一个名称，模型没有拿到本地函数本身。程序用工具注册表把这个名称对应到读取函数，再由读取函数检查参数。模型写出一个程序没有登记的名称，程序也不会因此执行新的操作。

### 有工具的 Agent Loop

本章完成后的控制流如下：

```text
+-------------+      +-------+      +----------------+
| user prompt | ---> | Model | ---> | final answer？ |
+-------------+      +---^---+      +-------+--------+
                         |                  | 是
                         |                  v
                         |            提交本轮消息
                         |                  |
                         |                  v
                         |              返回终端
                         |
                         |                  | 否
                         |                  v
                         |          +----------------+
                         |          | tool call(s)   |
                         |          | id/name/args   |
                         |          +-------+--------+
                         |                  v
                         |          +----------------+
                         |          | validate       |
                         |          | execute locally|
                         |          +-------+--------+
                         |                  v
                         +---------- tool result
                              使用同一个调用 ID
```

程序每次调用模型，只得到当前一步的决定。返回最终回答时，本轮结束；返回工具请求时，本地执行工具，把结果加入消息，再次调用模型。这就是 Agent Loop 中真正的“循环”。

这里还有第二个循环：第二章的终端 `while` 等待用户连续输入多条消息。两者不要混在一起：

```text
终端会话循环
  读取第 1 条用户输入
    -> Agent Loop：模型 -> 工具 -> 模型 -> 最终回答
  读取第 2 条用户输入
    -> Agent Loop：模型 -> 可能的工具 -> 最终回答
  读取 /exit
    -> 结束进程
```

外层循环等待用户的下一条输入，内层循环尝试完成当前这条要求。第 04 章增加搜索、第 06 章增加编辑、第 07 章增加测试命令时，仍复用这个内层结构。

## 数据怎样在循环中变化

以“读取 `package.json` 并告诉我包名”为例，本轮候选消息依次变成：

```text
1. user
   请读取 package.json，告诉我包名。

2. assistant
   toolCalls = [
     { id: "call_42", name: "read_file", arguments: "{\"path\":\"package.json\"}" }
   ]

3. tool
   toolCallId = "call_42"
   content = "{ ...package.json 的真实内容... }"
   isError = false

4. assistant
   这个包名是 @sherlockmen/hello-my-agent。
```

第 2 条和第 3 条通过 `call_42` 配对。名称说明调用哪个工具，ID 说明结果属于哪一次调用。一个响应可能包含多个工具请求，只靠工具名无法区分相同工具的多次调用，因此调用 ID 必须原样保存。

### 为什么本章按顺序执行多个工具

模型一次响应可能返回多个工具请求。本章使用 `for...of` 按返回顺序逐个执行，没有直接使用 `Promise.all()` 并行运行。

这是因为“同时收到多个请求”不等于“程序已经证明它们可以安全并发”。同一次模型响应中的请求是一起生成的，后一个请求不可能依赖前一个请求尚未产生的结果；真正的数据依赖必须经过“工具结果回到模型 → 模型再次决策 → 产生新请求”。

本章先逐个执行，便于看清“哪个请求得到了哪个结果，以及发生异常时停在哪里”。我们还没有实现并发调度，也没有记录工具会访问哪些资源。等第 06、07 章加入写文件和命令执行，同一批操作还可能相互影响，不能仅凭它们一起出现就全部并行。

后续要加入并发时，需要先区分这些情况：

```text
模型一次返回多个工具请求
            |
            v
     判断依赖和副作用
       /           \
只读且确认互不影响   写入或资源关系不明确
      |                 |
受控并发执行          串行或隔离执行
      |                 |
      +--------+--------+
               v
     按 toolCallId 配对结果
               |
               v
       一次性发回模型
```

并发也要限制同时运行的数量，并处理取消和单项失败。第 07、08 章先补充进程控制与取消，第 25 章引入子 Agent，第 27 章再讲并发调度。本章先把请求和结果的对应关系做清楚。

这些消息先保存在当前函数的 `turn` 数组中。只有模型最终返回可用回答，程序才执行 `history.push(...turn)`。如果请求被取消、出现意外异常或达到轮次上限，原来的会话历史保持不变。这样，下一次输入不会继承一段缺少结果或缺少最终回答的半成品消息链。

## `read_file` 的信任边界

工具定义中的 JSON Schema 会告诉模型：参数必须是包含 `path` 的对象。Schema 可以提高模型生成正确参数的概率，却不是安全检查。模型输出、网络响应和恢复的旧会话都可能包含无效或恶意数据，本地执行前必须重新验证。

本章按下面顺序检查：

```text
arguments 是有效 JSON？
  -> 是对象且只包含 path？
  -> path 是非空字符串？
  -> path 是相对路径？
  -> 检查时 realpath 位于当前项目根目录？
  -> 不是 .env、.env.* 或 .envrc？
  -> 目标是普通文件？
  -> 文件不超过 64 KiB？
  -> 按 UTF-8 解码
```

`resolve()` 只能处理文字路径，不能发现符号链接指向哪里。因此代码再调用 `realpath()`，比较项目根目录和目标文件在检查时的真实位置。表面路径即使写成 `project/link.txt`，只要它在检查时已经指向项目外，程序就会拒绝。

检查和真正读取文件是前后两个操作。如果另一个进程恰好在中间替换路径，读取目标仍可能变化。因此当前实现适用于使用者控制的本地工作区，不是抵抗恶意并发替换的文件系统沙箱。第 05 章会说明应用层审批为什么仍不等于沙箱，第 33 章再接入操作系统级隔离；第 04 章讨论的是多次分段读取之间文件内容可能变化，是另一类问题。

`.env`、`.env.*` 和 `.envrc` 常保存模型密钥或其他凭据，本章直接拒绝读取。程序还会检查符号链接解析后的真实文件名，避免通过另一个名字读取同目录中的 `.env`。这条硬性规则只挡住最明显的凭据文件，不等于完整权限系统；第 05 章会加入 allow、ask、deny 和审批范围。

程序会先拒绝检查时超过 64 KiB（65,536 字节）的文件，避免直接读入普通的大文件；检查后文件仍可能变化，因此这个大小检查也依赖前面说的可信工作区假设。Node 按 UTF-8 解码文件，无效字节会变成替代字符；本章没有验证文件编码。第四章会加入分段读取、文件发现、内容搜索和更完整的结果上限。

## 两种模型协议怎样进入同一个核心

OpenAI 兼容接口和 Anthropic 对工具消息使用不同字段：

| 含义 | OpenAI 兼容接口 | Anthropic |
| --- | --- | --- |
| 工具定义 | `tools[].function` | `tools[]` |
| 模型请求工具 | `assistant.tool_calls[]` | `assistant.content[].type = tool_use` |
| 工具结果 | `role = tool` | `user.content[].type = tool_result` |
| 配对字段 | `tool_call_id` | `tool_use_id` |

`models/client.ts` 负责这些差异。它把服务商响应统一成 `ToolCall { id, name, arguments }`，也把本地 `Message[]` 转回各协议需要的结构。`agent/agent-loop.ts` 只处理统一消息，因此同一套控制逻辑可以服务两种接口。

第 23 章还会补充流式工具参数、附件、能力判断和运行中模型切换。本章只实现非流式文本与 `read_file` 所需的最小协议子集。

## 成功与失败怎样结束

本章区分三类结果：

| 结果 | Agent Loop 怎样处理 | 是否提交本轮历史 |
| --- | --- | --- |
| 最终回答 | 返回终端 | 是 |
| 可预期工具错误 | 作为 `isError: true` 的工具结果发回模型，继续循环 | 最终成功后一起提交 |
| 取消、意外异常、8 次后仍无最终回答 | 停止并向外抛错 | 否 |

文件不存在、参数错误和未知工具属于可预期工具错误。模型看到真实错误后，可以换一个已知路径、修正参数，或者向用户解释无法完成。程序不会把错误伪装成文件内容。

内部编程错误不直接发给模型，也不原样显示给终端。错误信息可能包含系统路径、响应体或凭据，仍由 `errors.ts` 的安全边界处理。

## 模块边界

```text
src/
  cli.ts                 读取命令选项，装配并启动
  config/load-config.ts  读取模型配置，声明当前能力
  models/client.ts       转换两种模型协议和统一消息
  agent/agent-loop.ts    控制请求、工具执行、继续与停止
  tools/read-file.ts     校验参数和路径，读取文件
  tools/registry.ts      暴露工具定义，按名称分派执行
  ui/terminal.ts         读取多轮输入并显示回答
  errors.ts              定义安全错误类型，把外部异常转换成提示
```

`read-file.ts` 不调用模型，`models/client.ts` 不读取磁盘，`terminal.ts` 不决定工具步骤。每个模块只拥有自己的状态和副作用，问题发生时可以沿着调用链定位。

## 学完以后，我们能解释什么

- 模型提出工具请求后，为什么仍要由本地程序检查并执行。
- 调用 ID 怎样把文件内容或失败原因对应到原请求。
- 为什么读取结束后还要再次请求模型，最终回答才可能使用文件内容。
- 哪些工具错误可以反馈，哪些异常或取消应当停止。
- 为什么本轮消息先放在 `turn`，得到最终回答后才加入 `history`。

## 当前限制

Agent 现在可以读取已知路径的小文件，也能把失败原因交回模型。但它还不会回答“登录逻辑在哪个文件”这类只有目标、没有路径的问题。下一章会加入文件发现、内容搜索和分段读取，让模型先找位置，再读需要的代码。

本章没有权限确认：除了明确拦截的 `.env` 系列文件，项目内其他可读小文件都可能被工具返回给模型。第 05 章会再区分直接允许、询问用户和拒绝。
