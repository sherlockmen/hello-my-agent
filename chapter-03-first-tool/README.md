# 第 03 章：第一个工具与 Agent Loop

[全书目录](../README.md) · [03.1 识别工具请求](01-tool-request/README.md) · [03.2 执行并回传](02-read-file-loop/README.md) · [03.3 工具失败反馈](03-error-boundary/README.md) · [练习与答案](EXERCISES.md)

**本章目标：让模型通过 `read_file` 读取当前项目根目录中的真实文件，并理解一个有工具的 Agent Loop 如何请求、执行、反馈和结束。**

第二章的 `agentLoop()` 每轮只调用一次模型。模型可以解释代码，却不知道当前目录中实际有哪些内容。第三章加入第一个只读工具：模型决定是否请求读取，Node.js 程序校验并读取文件，再把结果交还模型。模型根据真实结果继续判断，直到返回最终回答。

前两章已经完成的命令能力继续保留：`hello-my-agent --doctor` 可以在不读取模型配置的情况下显示运行环境，连续会话中的 `/reset` 可以清空历史且不会发送给模型。本章只在这些能力之上增加工具请求和执行循环。

## 问题

假设你在项目目录中提问：

```text
请读取 package.json，告诉我这个包叫什么。
```

只有文本对话能力时，模型面临两个选择：承认不知道，或者根据上下文猜测。即使它说“我会读取文件”，这句话也不会触发操作系统打开文件。模型调用和文件系统属于两个不同的执行环境：

- 模型服务接收消息并返回一次结果。
- 本地 Agent 进程拥有文件系统 API，可以真正读取文件。

要把两者连接起来，程序必须让模型返回结构化工具请求，自己执行请求，再把真实结果发回模型。一次请求不一定结束，程序还要控制下一轮、失败分支和停止条件。

所以，本章要解决的问题是：**怎样让模型基于真实文件作答，同时保证工具参数经过校验、请求与结果正确配对、循环不会无限继续？**

阅读源码时，先打开每个小节的 `src/agent/agent-loop.ts`。这个文件固定保存当前阶段的全局主流程图：03.1 增加工具请求分支，03.2 接通执行与回传，03.3 再把工具错误接回循环。其他源码文件头部画的是各自节点内部的局部流程，并会明确指向这张全局图。这样可以先看清整条控制流，再分别理解协议转换、工具校验和终端交互。

## 完整执行模型

### 模型不能直接调用本地函数

“模型调用工具”是一种便于交流的简称。实际过程是：模型返回一段结构化数据，本地程序看到数据后决定是否执行。

```text
模型返回：
{
  id: "call_42",
  name: "read_file",
  arguments: "{\"path\":\"package.json\"}"
}

本地程序执行：
readFileTool('{"path":"package.json"}')
```

模型没有 Node.js 进程的函数引用，也没有因为生成了 `name: "read_file"` 就自动获得文件权限。工具注册表只接受本地明确登记的名称，执行函数还会重新检查参数。这个边界是 Coding Agent 能否可信运行的基础。

### 有工具的 Agent Loop

本章完成后的控制流如下：

```text
+-------------+      +-------+      +----------------+
| user prompt | ---> | Model | ---> | final answer？ |
+-------------+      +---^---+      +-------+--------+
                         |                  | 是
                         |                  v
                         |            提交本轮消息
                         |                  |
                         |                  v
                         |              返回终端
                         |
                         |                  | 否
                         |                  v
                         |          +----------------+
                         |          | tool call(s)   |
                         |          | id/name/args   |
                         |          +-------+--------+
                         |                  v
                         |          +----------------+
                         |          | validate       |
                         |          | execute locally|
                         |          +-------+--------+
                         |                  v
                         +---------- tool result
                              使用同一个调用 ID
```

程序每次调用模型，只得到当前一步的决定。返回最终回答时，本轮结束；返回工具请求时，本地执行工具，把结果加入消息，再次调用模型。这就是 Agent Loop 中真正的“循环”。

这里还有第二个循环：第二章的终端 `while` 等待你连续输入多条消息。两者不要混在一起：

```text
终端会话循环
  读取第 1 条用户输入
    -> Agent Loop：模型 -> 工具 -> 模型 -> 最终回答
  读取第 2 条用户输入
    -> Agent Loop：模型 -> 可能的工具 -> 最终回答
  读取 /exit
    -> 结束进程
```

外层循环管理不同用户回合，内层循环完成一条用户目标。以后增加搜索、编辑和测试工具时，仍复用这个内层结构。

## 数据怎样在循环中变化

以“读取 `package.json` 并告诉我包名”为例，本轮候选消息依次变成：

```text
1. user
   请读取 package.json，告诉我包名。

2. assistant
   toolCalls = [
     { id: "call_42", name: "read_file", arguments: "{\"path\":\"package.json\"}" }
   ]

3. tool
   toolCallId = "call_42"
   content = "{ ...package.json 的真实内容... }"
   isError = false

4. assistant
   这个包名是 @sherlockmen/hello-my-agent。
```

第 2 条和第 3 条通过 `call_42` 配对。名称说明调用哪个工具，ID 说明结果属于哪一次调用。一个响应可能包含多个工具请求，只靠工具名无法区分相同工具的多次调用，因此调用 ID 必须原样保存。

### 为什么本章按顺序执行多个工具

模型一次响应可能返回多个工具请求。本章使用 `for...of` 按返回顺序逐个执行，没有直接使用 `Promise.all()` 并行运行。

这是因为“同时收到多个请求”不等于“这些请求可以同时执行”。两个工具之间可能存在依赖：前一个工具读取配置，后一个工具根据读取结果决定路径；以后加入写文件和执行命令后，两个工具还可能同时修改同一资源。如果程序没有判断依赖和副作用就直接并行，完成顺序会变得不确定，文件可能互相覆盖，某个请求失败时也很难决定其他请求应该继续还是取消。

生产环境通常把工具分成两类：

```text
模型一次返回多个工具请求
            |
            v
     判断依赖和副作用
       /           \
只读且互不依赖     写入或存在依赖
      |                 |
受控并发执行          串行或隔离执行
      |                 |
      +--------+--------+
               v
     按 toolCallId 配对结果
               |
               v
       一次性发回模型
```

“受控并发”还需要队列和并发上限，不能把任意数量的任务全部交给 `Promise.all()`。程序还要处理单项失败、超时、取消传播、结果顺序、接口限流和重复执行带来的副作用。这些机制依赖后续的 Shell、取消、子 Agent 和任务状态，本章先保留容易验证的串行执行。第 27 章将在同一个 Agent 调度结构上加入生产级工具并发与任务生命周期。

这些消息先保存在当前函数的 `turn` 数组中。只有模型最终返回可用回答，程序才执行 `history.push(...turn)`。如果请求被取消、出现意外异常或达到轮次上限，原来的会话历史保持不变。这样，下一次输入不会继承一段缺少结果或缺少最终回答的半成品消息链。

## `read_file` 的信任边界

工具定义中的 JSON Schema 会告诉模型：参数必须是包含 `path` 的对象。Schema 可以提高模型生成正确参数的概率，却不是安全检查。模型输出、网络响应和恢复的旧会话都可能包含无效或恶意数据，本地执行前必须重新验证。

本章按下面顺序检查：

```text
arguments 是有效 JSON？
  -> 是对象且只包含 path？
  -> path 是非空字符串？
  -> path 是相对路径？
  -> realpath 后仍位于当前项目根目录？
  -> 不是 .env、.env.* 或 .envrc？
  -> 目标是普通文件？
  -> 文件不超过 64 KiB？
  -> 按 UTF-8 解码
```

`resolve()` 只能处理文字路径，不能发现符号链接指向哪里。因此代码再调用 `realpath()`，比较项目根目录和目标文件的真实位置。表面路径即使写成 `project/link.txt`，只要链接最终指向项目外，检查也会拒绝。

`.env`、`.env.*` 和 `.envrc` 常保存模型密钥或其他凭据，本章直接拒绝读取。程序还会检查符号链接解析后的真实文件名，避免通过另一个名字读取同目录中的 `.env`。这条硬性规则只挡住最明显的凭据文件，不等于完整权限系统；第 05 章会加入 allow、ask、deny 和审批范围。

64 KiB（65,536 字节）是当前阶段的固定保护上限，避免一次把任意大文件放入内存和模型上下文。Node 按 UTF-8 解码文件，无效字节会变成替代字符；本章没有验证文件编码。第四章会加入分段读取、文件发现、内容搜索和更完整的结果上限。

## 两种模型协议怎样进入同一个核心

OpenAI 兼容接口和 Anthropic 对工具消息使用不同字段：

| 含义 | OpenAI 兼容接口 | Anthropic |
| --- | --- | --- |
| 工具定义 | `tools[].function` | `tools[]` |
| 模型请求工具 | `assistant.tool_calls[]` | `assistant.content[].type = tool_use` |
| 工具结果 | `role = tool` | `user.content[].type = tool_result` |
| 配对字段 | `tool_call_id` | `tool_use_id` |

`models/client.ts` 负责这些差异。它把服务商响应统一成 `ToolCall { id, name, arguments }`，也把本地 `Message[]` 转回各协议需要的结构。`agent/agent-loop.ts` 只处理统一消息，因此同一套控制逻辑可以服务两种接口。

第 23 章还会补充流式工具参数、附件、能力判断和运行中模型切换。本章只实现非流式文本与 `read_file` 所需的最小协议子集。

## 成功与失败怎样结束

本章区分三类结果：

| 结果 | Agent Loop 怎样处理 | 是否提交本轮历史 |
| --- | --- | --- |
| 最终回答 | 返回终端 | 是 |
| 可预期工具错误 | 作为 `isError: true` 的工具结果发回模型，继续循环 | 最终成功后一起提交 |
| 取消、意外异常、8 次后仍无最终回答 | 停止并向外抛错 | 否 |

文件不存在、参数错误和未知工具属于可预期工具错误。模型看到真实错误后，可以换一个路径、修正参数，或者向你解释无法完成。程序不会把错误伪装成文件内容。

内部编程错误不直接发给模型，也不原样显示给终端。错误信息可能包含系统路径、响应体或凭据，仍由 `errors.ts` 的安全边界处理。

## 模块边界

```text
src/
  cli.ts                 读取命令选项，装配并启动
  config/load-config.ts  读取模型配置，声明当前能力
  models/client.ts       转换两种模型协议和统一消息
  agent/agent-loop.ts    控制请求、工具执行、继续与停止
  tools/read-file.ts     校验参数和路径，读取文件
  tools/registry.ts      暴露工具定义，按名称分派执行
  ui/terminal.ts         读取多轮输入并显示回答
  errors.ts              定义安全错误类型，把外部异常转换成提示
```

`read-file.ts` 不调用模型，`models/client.ts` 不读取磁盘，`terminal.ts` 不决定工具步骤。每个模块只拥有自己的状态和副作用，问题发生时可以沿着调用链定位。

## 本章实现清单

- 定义 `read_file` 的名称、说明和 JSON Schema。
- 统一 OpenAI 与 Anthropic 的工具请求和结果消息。
- 校验 JSON、字段、相对路径、真实路径、`.env` 凭据文件、文件类型和大小。
- 用调用 ID 配对工具请求与结果。
- 在 `agentLoop()` 中执行“模型 → 工具 → 模型”。
- 把可预期工具失败反馈给模型。
- 用 8 次模型请求上限阻止无限循环。
- 保持整轮成功后再提交历史的规则。

## 当前限制

本章只有 `read_file`，并且一次读取完整的小文件。除硬性拒绝 `.env` 系列文件和项目根目录外路径外，Agent 还没有第 05 章的权限确认系统；不要把其他含凭据或私密内容的文件放进当前项目根目录。Agent 也不能列目录、搜索内容、选择行范围、修改代码或执行测试，终端尚不会实时显示工具正在运行。下一章先解决“怎样找到要读的代码”，再逐步加入权限、编辑、Shell、流式输出和 TUI。
