# 第 02 章：接通模型并持续对话

[全书目录](../README.md) · [上一章](../chapter-01-first-command/README.md) · [从 02.1 开始](01-configuration/README.md) · [本章练习](EXERCISES.md)

**本章目标：把第一章的本地命令扩展成一个能够读取配置、调用模型、保存会话上下文、切换接口协议并解释运行结果的 CLI Agent。**

第一次学习时，先阅读“六个小节怎样组成一条执行链”，然后直接进入 02.1，按小节完成代码。完成 02.6 后，再回到本页阅读“完整执行过程”和后面的原理总结；那时每个名词都已经在代码中出现过。

本章会反复使用三个词：CLI 是运行在终端中的命令行程序；Agent 是由程序控制、能够根据模型结果继续决定下一步的执行系统；TUI 是在终端中持续刷新界面的交互形式。本章先完成 CLI 对话，后续章节再把显示层升级成 TUI。

## 本章要解决的根本问题

第一章的程序完全运行在本机：读取参数，执行 JavaScript，向终端打印固定文字。模型不在这个进程里。它通常运行在远程服务中，只能通过网络接口接收结构化请求并返回结构化响应。

因此，“给 CLI 接上模型”并不是把一个函数导入进来，而是建立下面这条完整链路：

```text
+-------------+     +----------------+     +----------------+
| 用户输入    | --> | 本地 Node 进程 | --> | 模型服务配置   |
| argv / stdin|     | CLI + Agent    |     | key/model/url  |
+-------------+     +-------+--------+     +----------------+
                            |
                            v
                    +----------------+
                    | 组织消息与状态 |
                    | Agent Loop     |
                    +-------+--------+
                            |
                            v
                    +----------------+
                    | 协议适配       |
                    | OpenAI/Anthropic|
                    +-------+--------+
                            |
                            v
                    +----------------+
                    | HTTP(S) 请求   |
                    | JSON + Auth    |
                    +-------+--------+
                            |
              +-------------+-------------+
              | 成功                      | 失败
              v                           v
      +----------------+          +----------------+
      | 文本、用量、   |          | 网络、认证、   |
      | 停止原因       |          | 限流、服务错误 |
      +-------+--------+          +-------+--------+
              |                           |
              v                           v
      保存成功历史并显示          转成安全提示并显示
```

这一章实现的 Agent 还不会调用工具。它的核心价值是先把输入、状态、模型和输出之间的边界建立正确。第三章加入工具后，读文件和执行命令都会进入同一条 Agent Loop，而不需要重新设计基础结构。


## 完整执行过程

以 02.6 的连续对话为例，一次输入会经过下面这些步骤：

1. `readline` 从标准输入 `stdin` 取得一行文本。
2. 终端模块排除空行和 `/exit`，把普通文本交给 `agentLoop()`。
3. `agentLoop()` 复制已有历史，再追加本轮用户消息，得到候选消息数组。
4. 模型模块根据 `provider` 把统一消息转换成 OpenAI 或 Anthropic 的请求字段。
5. SDK 把 JavaScript 对象编码成网络请求，等待远程服务返回。
6. 模型模块检查响应，提取文本、token 用量和停止原因，转换成统一的 `Reply`。
7. `agentLoop()` 再次检查取消状态。只有请求成功且没有取消，才把用户消息和模型回答一起写入历史。
8. 终端显示回答和用量，然后等待下一行输入。

任何一步抛出异常，后面的成功路径都会停止。终端捕获异常并显示提示，`history` 保持在上一次完整成功的状态。

```text
                     一次用户输入
                          |
                          v
                +-------------------+
                | history + input   |
                | 候选上下文        |
                +---------+---------+
                          |
                          v
                +-------------------+
                | model.generate()  |
                +---------+---------+
                          |
             +------------+------------+
             | 失败或取消              | 成功
             v                         v
      history 保持不变          再检查取消状态
             |                         |
             v                +--------+--------+
          显示错误             | 已取消          | 未取消
                               v                v
                        history 保持不变   保存完整问答
                                                |
                                                v
                                           显示回答
```

## 02.1：配置本质上是进程的输入

程序启动时可以从三个地方得到配置：

- `process.argv`：启动命令后面的参数，例如 `--model`。
- `process.env`：操作系统交给当前进程的环境变量。
- `.env`：磁盘上的普通文本文件，需要程序主动读取和解析。

`.env` 不是 Node 自动拥有的全局配置。`readProjectEnv()` 从 `process.cwd()` 开始向父目录查找它，读到文本后用 `parseEnv()` 转成普通对象。程序在最近的 `package.json` 处停止查找，是为了把配置限制在当前项目内，避免意外读取上级目录中另一个项目的密钥。

同一个字段可能同时出现在多个来源中，因此必须规定确定的优先级：

```text
命令行选项 > process.env > 最近项目的 .env > 程序默认值
```

这不是简单地把三个对象合并。程序要为每个字段选择第一个非空值，然后把“可能缺失的输入”转换成“可以使用的配置”：

```text
Options：model?、baseUrl?  -->  检查与补全  -->  Config：apiKey、model、baseURL
```

`Options` 中的问号表示调用者可以不提供；`Config` 没有问号，表示下游拿到它后不必重复判断。这个转换点就是配置边界。缺少必填项、协议不支持或 URL 结构无效，都应该在网络请求之前失败。

`baseUrl` 是 Commander 解析 `--base-url` 后使用的本地选项名；`baseURL` 是模型 SDK 使用的字段名。配置模块负责完成这次命名转换。02.1 只能确认字段存在、地址结构有效，不能证明密钥、模型 ID 或远端服务真实可用；这些内容要到 02.2 发出请求后才能验证。

API Key 不做成命令行选项，因为命令参数可能出现在 shell 历史或进程列表中。配置对象也不能整体输出到日志，因为它已经包含密钥。

## 02.2：一次模型请求是怎样发生的

`--prompt` 最初只是当前进程内的一段 JavaScript 字符串。模型模块把它放进消息对象，再交给 SDK：

```ts
{ role: "user", content: "你好" }
```

SDK 主要完成四件事：

1. 把模型 ID、消息和其他参数编码成接口要求的 JSON。
2. 根据 `baseURL` 生成请求地址。
3. 添加认证信息并发送 HTTP(S) 请求；使用 HTTPS 时，传输过程还会建立 TLS 加密连接。
4. 把返回的 JSON 转成 JavaScript 对象，或在网络与 HTTP 失败时抛出异常。

`await` 会暂停当前 `async` 函数，等待 Promise 完成；它不会让操作系统停止，也不会阻塞整个 Node 事件循环。网络 I/O 由运行时等待，响应到达后，后续代码才继续执行。因此入口必须使用 `parseAsync()`，否则顶层代码无法正确等待异步的 `.action()`。

模型收到的不是一整段无结构文字，而是带角色的消息列表：

| 角色 | 来源 | 作用 |
| --- | --- | --- |
| `system` | 程序 | 规定助手身份、语言和能力边界 |
| `user` | 使用者 | 提出本轮问题 |
| `assistant` | 模型 | 表示之前已经完成的回答 |

模型接口可能返回空文本、工具调用或其他内容。当前章节只接受非空纯文本，因此必须在模型模块检查响应。未经检查的远程数据不能直接写入历史。

`Model` 是 TypeScript 的结构约束：只要对象提供兼容的 `generate(messages, signal)` 方法，就能交给 Agent Loop。TypeScript 编译后会删除接口和类型；运行时真正存在的是普通 JavaScript 对象、函数和 SDK 客户端。这就是为什么类型能帮助编译器检查边界，却不会替程序完成运行时响应校验。[TypeScript 官方文档](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch#erased-types)也将这种行为称为类型擦除。

## 02.3：Agent Loop 是状态转换规则

Agent Loop 不是“文件名里有 loop”或者“必须先写一个 `while`”。它表示 Agent 完成一项任务时反复遵守的控制规则：准备上下文、调用模型、检查结果、执行下一步，直到产生最终回答或达到停止条件。

本章还没有工具，模型直接返回文本，所以一轮执行只调用模型一次：

```text
当前状态 + 用户输入 --> 模型调用 --> 新状态 + 回答
```

第三章加入工具后，同一个位置会扩展为：

```text
调用模型 --> 有工具请求？
               | 是 --> 执行工具 --> 追加工具结果 --> 再调用模型
               | 否 --> 返回最终回答
```

当前 `agentLoop()` 最关键的地方不是循环次数，而是**状态提交时机**。它先用展开语法创建候选数组：

```ts
const messages = [...history, userMessage];
```

这一步不会修改原历史。只有模型成功返回，并且第二次取消检查也通过，程序才执行：

```ts
history.push(userMessage, { role: "assistant", content: reply.text });
```

这类似一次小型事务：先准备候选状态，外部操作成功后再提交。如果请求失败、超时或被取消，历史仍停留在上一次完整状态，不会出现“只有问题、没有回答”的半轮数据。

请求前检查取消，避免已经取消的任务继续发出网络请求；响应后再次检查，避免请求返回和取消几乎同时发生时，把用户已经取消的结果写入历史。

## 02.4：多轮记忆来自本地重放

模型服务不会自动记住这个 CLI 进程之前说过什么。这里使用的接口是无状态调用：每次请求只根据本次请求体中的消息生成结果。

连续对话之所以像“有记忆”，是因为终端模块在进程堆内存中保存 `history`，下一轮把旧消息再次发送：

```text
第一轮请求：system + user(1)
第二轮请求：system + user(1) + assistant(1) + user(2)
第三轮请求：system + user(1) + assistant(1) + user(2) + assistant(2) + user(3)
```

因此，历史必须在输入循环外创建。放在循环内会让每轮都得到一个新数组，第二次请求就看不到第一轮。退出进程后，堆内存被操作系统回收，历史也随之消失；磁盘持久化要到后续会话章节实现。

历史越长，请求携带的输入 token 通常越多，延迟和费用也会增加。token 是模型读取和生成文本时使用的计量单位，它不固定等于一个汉字、一个单词或一个字符。成熟 Agent 会裁剪、总结或压缩上下文，本章先保留完整历史，便于看清机制。

终端中存在两种不同的循环：

- **输入循环**：等待一条用户输入，完成后再等下一条。
- **Agent Loop**：处理同一项任务内部的模型、工具和停止条件。

本章只实现第一种循环和 Agent Loop 的无工具路径。把两者区分开，后面加入工具时才不会把“等待用户”误写成“模型继续执行”。

[Node.js Readline](https://nodejs.org/api/readline.html) 把 `stdin` 这个字节流按行转换成字符串；异步迭代器依次取出每一行。EOF 表示输入流已经结束，在 macOS 和 Linux 的交互终端中通常按 Ctrl+D 产生。`/exit` 是本地命令，不发送给模型。Ctrl+C 产生 `SIGINT`，终端模块调用 `AbortController.abort()`，让正在等待的模型请求收到取消信号，然后关闭输入并设置退出码 130；130 是类 Unix 系统表示进程被 Ctrl+C 中断的常用退出状态。

## 02.5：统一接口隔离协议差异

OpenAI Chat Completions 和 Anthropic Messages 都接收对话并返回模型结果，但字段并不相同：

| 语义 | OpenAI 兼容接口 | Anthropic Messages |
| --- | --- | --- |
| 调用方法 | `chat.completions.create()` | `messages.create()` |
| 系统提示词 | `messages` 中的 `system` 消息 | 独立的 `system` 字段 |
| 对话消息 | `user` / `assistant` | `user` / `assistant` |
| 文本位置 | `choices[0].message.content` | `content` 中的 `text` 块 |
| 输出上限原因 | `finish_reason: length` | `stop_reason: max_tokens` |
| 用量字段 | `prompt_tokens` / `completion_tokens` | `input_tokens` / `output_tokens` |

如果 Agent Loop 直接处理这些字段，每增加一个服务商，核心就要增加一组条件分支。当前实现把差异限制在模型模块，对上层只暴露：

```ts
interface Model {
  generate(messages: Message[], signal: AbortSignal): Promise<Reply>;
}
```

这是一层协议适配：输入统一为 `Message[]`，输出统一为 `Reply`。`createModel()` 根据 `provider` 选择客户端，`requestReply()` 负责字段转换，Agent Loop 不知道请求最终去了哪个服务商。

配置也必须先选协议，再读取对应凭据。选择 `anthropic` 时只读取 `ANTHROPIC_*`，不能缺少 Anthropic Key 后回退到 OpenAI Key。密钥和目标地址必须属于同一个信任边界，否则程序可能把凭据发送给错误的服务。

[OpenAI Chat Completions](https://developers.openai.com/api/reference/typescript/resources/chat/subresources/completions/methods/create) 根据本次提交的消息列表生成回答；[Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create) 同样只处理本次请求中的结构化消息。两种调用都不会读取本地 `history` 变量：程序要么在下一轮重新提交旧消息，要么使用服务商另外提供的服务端会话机制。本章选择重新提交历史，因为数据流可以直接观察，也不依赖某一家服务商的会话 ID。

## 02.6：错误和用量也是接口输出

远程调用的结果不只有“回答文本”。程序至少还要处理：

- 网络无法连接或请求超时。
- HTTP 401、403、404、429 和服务端错误。
- 成功响应中缺少纯文本。
- token 用量缺失。
- 模型因为输出上限而提前停止。

SDK 错误可能包含远端响应、请求信息或调试细节。直接打印 `error.message` 会把外部数据带进终端日志，也可能泄露不应该展示的内容。因此 `explainError()` 只原样展示程序自己创建的 `UserFacingError`；外部错误只按错误类型和 HTTP 状态码映射为固定提示。

状态码说明“请求在哪一层失败”：

| 状态 | 含义 | 当前提示方向 |
| --- | --- | --- |
| 网络 / 超时 | 没有正常取得 HTTP 响应 | 检查网络、地址或稍后重试 |
| 401 | 身份认证失败 | 检查 API Key 与接口是否匹配 |
| 403 | 身份已识别，但没有访问权限 | 检查账号与模型权限 |
| 404 | 路径或模型不存在 | 检查基础地址与模型 ID |
| 429 | 达到额度或速率限制 | 检查额度或稍后重试 |
| 5xx | 服务端处理失败 | 稍后重试 |

token 用量必须使用服务商返回的统计，不能用字符串长度猜测。一个汉字、英文单词或标点不固定对应一个 token，服务端还可能对请求做额外转换。兼容接口不一定返回用量，所以本地类型使用 `number | null`；缺失时显示“未知”，而不是错误地显示 0。

`finish_reason: length` 或 `stop_reason: max_tokens` 表示本次输出达到上限。请求本身可能成功，但回答可能不完整，因此它属于成功结果中的停止信息，不属于异常。[Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create) 将 token 统计放在 `usage`，将停止原因放在 `stop_reason`；OpenAI 则使用 `usage.prompt_tokens`、`usage.completion_tokens` 和每项选择上的 `finish_reason`。模型模块把这些不同字段统一成 `inputTokens`、`outputTokens` 和 `truncated`，终端因此不需要理解服务商协议。

## 状态分别活多久

理解状态的生命周期，可以解释本章大部分行为：

| 状态 | 存放位置 | 生命周期 | 何时消失 |
| --- | --- | --- | --- |
| 命令行参数 | `process.argv` | 当前进程 | 进程结束 |
| 环境变量 | `process.env` | 当前进程 | 进程结束；不会自动写回 shell |
| `.env` 配置 | 磁盘文件 | 跨进程 | 文件被修改或删除 |
| `Config` | JavaScript 对象 | 当前启动过程 | 进程结束 |
| `history` | 堆内存数组 | 当前连续会话 | 退出 Agent 或重新创建数组 |
| 候选消息 | `agentLoop()` 局部数组 | 当前一轮 | 本轮返回或抛错 |
| 远程响应 | SDK 返回对象 | 当前一轮 | 无引用后由垃圾回收处理 |

本章没有数据库和会话文件，所以重启后不会恢复历史。模型服务也不会替这个本地程序保存 `history`；是否保存服务端日志是服务商政策问题，与本地多轮上下文机制不是一回事。

## 当前实现的能力边界

完成本章后，Agent 已经具备：

- 从项目配置中取得模型连接信息。
- 通过 OpenAI 兼容或 Anthropic 协议请求模型。
- 在一个进程内保持多轮文本上下文。
- 在失败时保留上一次完整历史。
- 取消正在执行的请求并正确结束终端。
- 显示服务商报告的 token 用量和输出截断提示。

它仍然不能读取文件、执行命令、调用工具、保存会话或流式显示回答。模型即使在文字中声称完成了这些操作，也只是生成了文本。真正的 Coding Agent 必须把模型提出的工具请求交给本地代码执行，再把结果返回模型；这是第三章的主题。

```bash
npm run lesson:02.1
npm run lesson:02.2
npm run lesson:02.3
npm run lesson:02.4
npm run lesson:02.5
npm run lesson:02.6
```

完成整章后运行：

```bash
npm run verify
```

它会使用本地模拟接口检查配置优先级、消息历史、协议转换、错误分类、取消和用量，不需要真实 API Key。真实服务只能验证账号权限、网络连通性和实际模型行为，不能替代这些确定性的程序检查。
