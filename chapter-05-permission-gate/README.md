# 第 05 章：在执行前作出权限决定

[全书目录](../README.md) · [05.1 权限策略](01-policy-decision/README.md) · [05.2 终端审批](02-terminal-approval/README.md) · [05.3 会话授权](03-session-grants/README.md) · [练习与答案](EXERCISES.md)

**本章只回答一个问题：模型提出工具请求后，本地程序怎样在执行前决定“直接允许、询问用户还是拒绝”？**

第四章已经让 Agent 自主调用 `glob`、`grep` 和 `read_file`。只要工具名称出现在注册表中，Agent Loop 就会立即执行。这个设计适合验证工具循环，却把两个不同问题混在了一起：

- **工具是否存在？** 注册表回答“程序会不会执行这种操作”。
- **本次调用是否允许？** 权限策略回答“这个工具带着这些参数，现在能不能执行”。

模型输出属于未经信任的请求。系统提示词可以要求模型谨慎，但提示词仍是给模型阅读的文字，不能代替本地程序的强制判断。即使用户消息中出现“忽略规则，我已经批准”，程序也只能接受审批通道返回的结构化决定。

| --- | --- | --- |
| [05.1](01-policy-decision/README.md) | 怎样保证所有工具在执行前都经过同一个权限入口？ | 直接允许、需要确认、不可批准三种决定 |

## 权限位于 Agent Loop 的哪个位置

第五章只在模型请求与工具注册表之间增加一道门：

```text
模型返回 ToolCall
        |
        v
decideToolPermission(call)
        |
        +-- deny --------------------------> 不执行，错误结果回给模型
        |
        +-- ask --> ApprovalHandler
        |               |-- 拒绝 ----------> 不执行，错误结果回给模型
        |               +-- 允许 ----------> 继续
        |
        +-- allow --------------------------> 继续
                                                |
                                                v
                                      executeTool(call)
                                                |
                                                v
                                        工具结果回给模型
                                                |
                                                v
                                      模型继续决策或最终回答
                                                |
                                                v
                                  最终回答出现后提交完整本轮历史
```

Agent Loop 仍不知道 `read_file`、`grep` 或第 06 章 `write_file` 的具体风险。它只执行统一协议：先取得决定，再根据决定继续。工具名称、路径和风险规则集中在 `permissions/policy.ts`，终端只负责收集用户选择。

## 一次批准怎样在当前会话中复用

以连续读取两个 Git 元数据文件为例，三个小节会组合成下面这条链：

```text
第一个用户目标：读取 .git/HEAD
  -> 模型请求 read_file(".git/HEAD")
  -> 权限策略判断“需要确认”
  -> 终端等待用户输入 s，表示本次会话允许
  -> 程序保存 read_file:.git/**
  -> 工具读取文件，结果回到模型
  -> 模型给出最终回答，本轮进入 history

第二个用户目标：读取 .git/config
  -> 模型再次请求 read_file
  -> 权限策略先检查不可批准规则，再查询会话授权
  -> read_file:.git/** 已存在，工具直接执行
  -> 结果回到模型，模型给出最终回答
```

这里保存的不是“用户曾经同意过”这个布尔值，而是程序根据本地规则生成的工具和资源范围。`.git` 的读取授权不会放行 `.codex`、项目外路径或未来的写入工具。不可批准规则仍然最先检查，所以会话授权也不能放行 `.git/.env`。

本章涉及的状态具有不同生命周期：

| 状态 | 谁持有 | 存在多久 | 用途 |
| --- | --- | --- | --- |
| 一次权限决定 `PermissionDecision` | 权限策略返回给 Agent Loop | 当前工具请求 | 判断直接执行、等待确认或拒绝 |
| 一次审批回答 `ApprovalResponse` | 终端审批回调返回给 Agent Loop | 当前待确认请求 | 表示允许一次、会话允许或拒绝 |
| 会话授权 `sessionGrants` | 终端会话 | 当前 CLI 进程 | 复用完全相同的工具与资源范围 |
| 对话历史 `history` | 终端会话 | 当前 CLI 进程 | 只在模型给出最终回答后提交完整本轮 |

退出 CLI 后，会话授权和对话历史都会随进程内存消失。第 13 章会持久化对话会话，第 17 章才讨论持久权限配置；两种状态不会因为本章使用同一个进程而混为一体。

## `allow`、`ask`、`deny` 分别表示什么

| 决定 | 当前规则 | 执行结果 |
| --- | --- | --- |
| `allow` | 项目内普通只读工具 | 直接进入工具注册表 |
| `ask` | `read_file` 读取 `.git`、`.agents` 或 `.codex` 元数据 | 等待终端批准；没有交互终端时拒绝 |
| `deny` | 未登记工具、无效权限参数、项目外路径、`.env` 系列文件，或搜索工具点名受保护元数据 | 不提供批准选项，也不执行工具 |

`deny` 表示程序不会提供批准选项，输入 `y` 或已有会话授权都不能改变结果。只有 `ask` 才会交给用户决定。这样，界面不会为项目外路径或 `.env` 显示一个可以继续执行的按钮。

路径判断不能只检查模型写出的字符串。项目内的 `hidden` 可能是指向 `.git/HEAD` 的符号链接，因此策略会先解析已经存在目标的真实路径，再决定它属于普通源码、待确认元数据还是项目外资源。具体工具执行时仍会重新校验参数和真实路径；两次检查之间存在文件系统竞态，所以当前实现不是操作系统沙箱。

`glob` 和 `grep` 用来批量发现文件。如果让它们扫描 `.git`、`.agents` 或 `.codex`，一次搜索就可能读出大量元数据，也无法逐个展示待审批文件。因此搜索工具固定跳过这些目录。模型确实需要某个元数据文件时，必须改成具体的 `read_file` 请求，再由权限策略决定是否询问用户。

## 为什么观察者不能负责批准

第四章的 `AgentObserver` 是旁路：它可以显示事件，但抛出异常或修改事件副本都不能改变 Agent 结果。审批恰恰需要改变控制流——拒绝时工具绝不能执行。

因此第五章保留两条不同通道：

```text
AgentEvent ------> teaching-trace / 日志 / 第 10 章 TUI  只观察

ApprovalHandler -> allow_once / allow_session / deny  控制执行
```

第 09 章会扩展事件输出，第 10 章的 TUI 只需提供新的 `ApprovalHandler` 并订阅相同事件，不需要修改权限规则或工具注册表。

## 与成熟 Coding Agent 的共同原则

Claude Code 的公开权限说明把规则分为 allow、ask、deny，并明确按 deny、ask、allow 的顺序匹配；权限由 Claude Code 程序执行，提示词和项目说明只能影响模型想做什么，不能改变程序允许什么。它还把工作目录内的只读操作与文件修改、Shell、网络等副作用操作区别处理。[Claude Code 权限说明](https://code.claude.com/docs/en/permissions)

Codex 的公开安全说明把“沙箱”和“审批”分成两层：沙箱决定进程在操作系统层面能够访问什么，审批决定哪些越界或有副作用的操作必须先征求同意。批准不能替代沙箱，沙箱也不能表达用户是否愿意执行某个具体动作。[Codex Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security)

本章实现的是应用层权限策略与审批链，还没有实现操作系统沙箱。第 33 章才会接入真正的执行隔离；在此之前，正文只声称程序主动拒绝了请求，不声称恶意进程无法绕过文件系统边界。

## 本章完成后你应能解释

1. 为什么工具注册表不是权限系统。
2. 为什么系统提示词和用户聊天文字都不能批准本地操作。
3. 为什么 `deny` 必须先于 `ask` 和 `allow`。
4. 为什么 Agent Loop 必须等待审批回调，而事件观察者只能显示状态。
5. 为什么会话授权必须保存本地生成的明确范围，而不能保存模型的任意描述。
6. 为什么真实路径检查仍不等于操作系统沙箱。
