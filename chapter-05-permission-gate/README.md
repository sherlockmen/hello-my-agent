# 第 05 章：工具执行之前，先检查权限

[全书目录](../README.md) · [05.1 权限策略](01-policy-decision/README.md) · [05.2 终端审批](02-terminal-approval/README.md) · [05.3 会话批准](03-session-grants/README.md) · [练习与答案](EXERCISES.md)

第四章的 Agent 已经能找到文件、搜索代码，再读取相关内容。接下来，我们让它回答一个看似普通的问题：当前仓库使用哪个 Git 分支？模型可能为此请求读取 `.git/HEAD`。程序虽然会读这个文件，但还需要回答另一件事：这次读取可以直接进行，还是应该先征求用户同意？

工具注册表只能找到 `read_file` 的实现，不能替用户回答这个问题。本章在工具执行之前加入权限判断。普通源码可以直接读取，Git 等项目元数据先询问用户，`.env` 这类可能保存凭据的文件则直接拒绝。这样，模型负责提出完成任务所需的操作，本地程序负责检查哪些操作可以真正发生。

## 三个小节怎样接起来

| 小节 | 我们要解决的问题 | 完成后的变化 |
| --- | --- | --- |
| [05.1](01-policy-decision/README.md) | 同一个读取工具，访问不同文件时为什么不能一律放行？ | 在执行前给出允许、需要确认或拒绝的结果 |
| [05.2](02-terminal-approval/README.md) | 需要确认时，程序怎样等到用户回答后再继续？ | 终端显示请求，用户允许一次或拒绝，工具结果回到模型 |
| [05.3](03-session-grants/README.md) | 连续读取 `.git/HEAD` 和 `.git/config`，怎样避免反复询问？ | 记住本次运行已批准的工具和目录，下一次先检查是否适用 |

每节都在前一节上增加一件事。05.1 先识别需要确认的请求，还不能实际询问；05.2 接上终端输入；05.3 才让用户选择是否记住批准。三个步骤完成后，权限判断就能参与完整的 Agent Loop。

## 一次工具请求怎样经过检查

权限检查放在模型请求和工具执行之间。它的三个返回值分别是 `allow`、`ask` 和 `deny`：

```text
模型返回 ToolCall
        |
        v
decideToolPermission(call)
        |
        +-- deny --------------------------> 不执行，错误结果回给模型
        |
        +-- ask --> ApprovalHandler
        |               |-- 拒绝 ----------> 不执行，错误结果回给模型
        |               +-- 允许 ----------> 继续
        |
        +-- allow --------------------------> 继续
                                                |
                                                v
                                      executeTool(call)
                                                |
                                                v
                                        工具结果回给模型
                                                |
                                                v
                                      模型继续决策或最终回答
                                                |
                                                v
                                  最终回答出现后提交完整本轮历史
```

`allow` 表示可以继续调用工具；`ask` 表示先等用户确认；`deny` 表示这次请求不允许执行，也不提供批准选项。比如 `.git/HEAD` 可以询问，而 `.env` 不能通过输入 `y` 放行。

Agent Loop 只按这个结果安排后续步骤，不需要自己判断 `.git` 是什么目录。具体规则放在 `permissions/policy.ts`，终端负责显示问题和读取选择，工具仍负责校验参数并读取文件。读取成功或失败，模型都会收到与原请求对应的结果，再决定怎样继续回答。

## 同一类读取，怎样少问一次

连续查看 Git 信息时，用户可能愿意在这次运行中允许读取整个 `.git` 目录，而不只是眼前的一个文件。05.3 会把这项选择保存下来：

```text
第一个用户目标：读取 .git/HEAD
  -> 模型请求 read_file(".git/HEAD")
  -> 权限策略判断“需要确认”
  -> 终端等待用户输入 s，表示本次会话允许
  -> 程序保存 read_file:.git/**
  -> 工具读取文件，结果回到模型
  -> 模型给出最终回答，本轮进入 history

第二个用户目标：读取 .git/config
  -> 模型再次请求 read_file
  -> 权限策略先检查不可批准规则，再查询会话授权
  -> read_file:.git/** 已存在，工具直接执行
  -> 结果回到模型，模型给出最终回答
```

程序保存的不是“用户同意过”这个布尔值，而是 `read_file:.git/**` 这样的记录：允许哪个工具，读取哪个项目内目录。下一次读取 `.git/config` 会得到相同记录，所以可以复用；读取 `.codex/note.txt` 则需要另外确认。

每次请求仍要先检查禁止规则。即使已经允许读取 `.git`，`.git/.env` 也会先被拒绝，不会因为批准记录存在就放行。

这些数据分别在什么时候有效，也要说清楚：

| 数据 | 谁保存 | 保存多久 | 用来做什么 |
| --- | --- | --- | --- |
| 权限判断 `PermissionDecision` | 策略交给 Agent Loop | 当前工具请求 | 说明可以继续、需要确认还是必须拒绝 |
| 审批回答 `ApprovalResponse` | 终端交给 Agent Loop | 当前待确认请求 | 说明允许一次、记住批准还是拒绝 |
| 批准记录 `sessionGrants` | 终端会话 | 当前 CLI 进程 | 下一次请求时检查能否复用 |
| 对话历史 `history` | 终端会话 | 当前 CLI 进程 | 把已完成的对话继续发给模型 |

退出 CLI 后，内存中的批准记录和对话历史都会消失。但它们用途不同：`/reset` 只清空对话，不撤销批准；章末练习会增加单独的撤销命令。第 13 章再讨论保存对话，第 17 章讨论持久权限配置。

## 哪些读取可以批准

本章仍然只有只读工具。为了把审批过程做出来，我们选取了三种实际请求：

| 请求 | 当前规则 | 为什么这样处理 |
| --- | --- | --- |
| 读取普通项目源码 | `allow` | 是完成代码任务时经常需要的读取 |
| 用 `read_file` 读取 `.git`、`.agents`、`.codex` 中的具体文件 | `ask` | 先说明要读取什么，再由用户确认 |
| 访问 `.env` 系列、项目外路径、未知工具或无效权限参数 | `deny` | 这些请求没有批准入口 |
| 用 `glob`、`grep` 点名搜索上述元数据目录 | `deny` | 批量搜索不能绕过具体文件的审批 |

宽泛的搜索也会跳过这些元数据目录。模型如果确实需要其中的文件，要提出具体的 `read_file` 请求。路径检查还会解析符号链接，避免把指向 `.git/HEAD` 的普通文件名当成普通源码直接放行。

这些检查都由当前程序主动执行。检查路径和随后打开文件之间仍可能发生其他修改，所以它们不等于操作系统沙箱。第 33 章才会加入更强的执行隔离。

## 显示进度和取得批准，为什么要分开

第四章的观察者可以显示“工具即将开始”，但程序不会根据观察者的返回值决定是否执行。审批不同：用户拒绝后，工具必须停下来。因此，本章保留两条不同的通道：

```text
AgentEvent ------> teaching-trace / 日志 / 第 10 章 TUI  只观察

ApprovalHandler -> allow_once / allow_session / deny  控制执行
```

`AgentEvent` 告诉界面发生了什么，`ApprovalHandler` 则返回用户的选择，Agent Loop 必须等待它。第 09 章扩展事件输出、第 10 章换成 TUI 后，这两项职责仍然成立。

聊天消息里的“我已经批准”也不能代替审批。聊天文字会发给模型，而是否执行工具取决于本地权限判断和审批回答；模型不能用一句“用户已同意”改写这个结果。

## 与成熟 Coding Agent 的共同做法

Claude Code 的公开权限说明同样区分 allow、ask、deny，并按 deny、ask、allow 的顺序匹配。提示词可以影响模型想做什么，真正允许执行什么仍由程序检查。[Claude Code 权限说明](https://code.claude.com/docs/en/permissions)

Codex 的公开说明还区分了审批和沙箱：审批处理是否需要用户同意，沙箱限制进程实际能够访问什么。我们在本章实现前一部分，不能因此宣称已经获得操作系统层面的隔离。[Codex Agent approvals & security](https://developers.openai.com/codex/agent-approvals-security)

## 完成这一章以后

我们将能沿着一次请求解释清楚：模型提出了什么，程序为什么询问或拒绝，用户的回答怎样影响执行，以及结果怎样回到模型。连续读取时，还能判断一次批准为什么可以复用到另一个文件，又为什么不能放行其他目录或禁止操作。

第六章会让 Agent 真正创建和修改文件。到那时，光问“是否允许访问这个文件”还不够，还要把具体修改展示出来，让用户看过后再批准。本章的权限入口和审批等待会继续使用，写入则要逐次确认，不能直接沿用只读批准。

从 [05.1](01-policy-decision/README.md) 开始，先把权限判断放到工具执行之前。
